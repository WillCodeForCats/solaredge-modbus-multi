# Problems with shared units and the shared connection

By default this integration does not own its Modbus/TCP connection. It gets a
unit per Device ID on the connection the Home Assistant `modbus` integration
shares per host and port (`async_get_unit` for polling,
`async_get_temporary_unit` for scanning). That keeps the inverter's single TCP
connection from being fought over, but the connection's settings belong to all
of its users. This document collects the problems that follow from that.

The alternative is a direct connection (options: _Modbus Connection_), which
has its own timeout and message spacing that other integrations cannot change.

## Summary

_Generated by Claude Code from the code on the `ha-modbus-connection` branch._

- In the default mode, polling uses a unit per Device ID from
  `async_get_unit` (`__init__.py`). Each unit gets our message spacing and
  `require_timeout(request_timeout)`; `SharedUnits` in `hub.py` wraps them.
  Scanning uses `async_get_temporary_unit` (`scanner.py`).
- The connection and its timing settings are shared. A unit can only raise the
  timeout, so the highest request from any integration applies to all of them,
  and it stays until the connection is closed and reopened.
- The main consequence is slow or missed updates while another integration
  such as the built-in SolarEdge Modbus asks for 30 seconds, and very slow
  setup scans, because `scan_timeout` only takes effect on a shared unit when
  we are the first on the connection.
- The code works around parts of this: our spacing is re-applied before every
  request, the battery probe skips its own timeout on shared units, the
  `shared_connection_other_integration` repair issue reports another
  integration holding the connection (detected through the modbus
  integration's `async_get_connection_info`, not by timing refreshes), and a
  direct connection or socket scan avoids the shared timeout entirely.
- It cannot fix the lingering timeout. That needs a Home Assistant restart.

## 1. Another integration forces a long timeout

The shared connection uses the highest timeout any holder asks for, and a unit
can only raise it. Home Assistant's built-in SolarEdge Modbus integration
(`solaredge_modbus`) asks for 30 seconds, and its timeout is fixed. Our default
is 3 seconds (option _Modbus Request Timeout_), so the 30 seconds wins for every
request on the connection, ours included.

Effects:

- A request that is slow to fail holds up polling, so refreshes can take
  minutes, updates are slow or missed, and entities go unavailable.
- Either integration can change the other's message spacing on a shared unit.
  Enforcing our own spacing before every attempt is deliberate (see
  `component_update` in `hub.py`).
- The "Another Integration Shares This Inverter" repair issue is raised while
  polling when another config entry holds units on the same device. It does
  not time anything, because the link's timeout cannot be read; another holder
  is only the closest sign that a long timeout may be forced on us.

## 2. The long timeout lingers

Disabling or removing the other integration does not shorten the timeout. The
connection keeps the highest timeout it was given until it is closed and
reopened, which in practice means restarting Home Assistant.

This includes trying the built-in integration only briefly: once it has asked
for 30 seconds, the timeout stays until the restart.

## 3. Scanning is slow

Scanning for inverters goes through temporary units on the shared connection,
so `scan_timeout` can only shorten the wait if we are the first on the
connection (a unit can only raise the timeout). A scan waits out the full timeout
for every silent Device ID (one that does not answer), on each attempt
(`scan_retries`). IDs where the gateway answers with `GatewayPathUnavailableError`
or `GatewayTargetError` return `NOT_FOUND` immediately, without retrying.

Worst case with a 30 second timeout and 1 inverter:

| Scan          | IDs scanned | 3 attempts (90 s/ID) | 2 attempts (60 s/ID) | 1 attempt (30 s/ID) |
| ------------- | ----------- | -------------------- | -------------------- | ------------------- |
| Fast Scan     | 1–32        | ~45 minutes          | ~30 minutes          | ~15 minutes         |
| Complete Scan | 1–247       | ~6 hours             | ~4 hours             | ~2 hours            |

These are arithmetic, not measurements. With the default 3 second timeout the
same scans take a few minutes. The config flow's scan uses 2 attempts.

Effects:

- Setup can look stalled.
- Other integrations on the connection queue behind the scan, so they are held
  up as well.

Ways around it:

- Use the manual setup with known Device IDs, which does not scan.
- Disable the other integration and restart Home Assistant before scanning.
- Scan over our own socket (`SolarEdgeDeviceScanner(use_socket=True)`). The
  `scan_timeout` is then honored and empty IDs fail fast. The cost is no
  coordination with the shared connection, and an inverter accepts few TCP
  connections at once, so scanning while another client holds it can fail to
  connect. The config flow does not use this yet.

## 4. Waiting in line is not the device's response time

A request on a shared unit can wait behind other consumers before it is sent.
A timeout that wraps the whole call counts that wait as if the device had not
answered.

- **Battery probe (fixed).** `SolarEdgeBattery.init_device` wrapped its probe in
  `asyncio.timeout(request_timeout)`, so a busy shared connection could reject a
  battery that was present as `DeviceInvalid`. It now skips that outer timeout
  on a shared connection; the per-request timeouts and the setup watchdog
  (`REFRESH_WATCHDOG`, 240 seconds) bound the probe instead. Owned connections
  keep the cap.
- **Scanner (no problem).** A review comment suggested queue wait could make a
  valid device come back `NOT_FOUND` in `scan_device_id`. It cannot today: the
  `asyncio.wait_for` was removed in commit `342f299`, so only the library's
  per-request `ModbusTimeoutError` applies, which retries and ends in
  `NOT_FOUND` after the last attempt, as intended for a silent ID. The
  gateway-error branch (`GatewayPathUnavailableError`, `GatewayTargetError`)
  is the gateway saying nothing is at that ID, not a timeout. If a local
  timeout is ever added back to unit scans, it must account for queue wait
  separately from the device's response time, or report an inconclusive result.

## 5. Running both integrations

Running this integration and the built-in SolarEdge Modbus integration
(`solaredge_modbus`) for the same inverter is not recommended.

- Home Assistant may offer to set up the built-in integration when it
  discovers your inverter. Check that you are adding the one you intend to use.
- If this integration raises the "Another Integration Shares This Inverter"
  repair issue, disable the other integration for this inverter and restart Home
  Assistant.
- If you know your Device IDs, use the manual setup (no scan). Otherwise,
  disable the other integration and restart Home Assistant before adding this
  one.

If you want to run both anyway, open the options of this integration and change
the _Modbus Connection_. It has three choices:

| Modbus Connection                                         | What it does                                                                                                                 |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Use the Home Assistant shared Modbus connection (default) | Shares one Modbus/TCP connection with other integrations that talk to the same inverter.                                     |
| Use direct connection                                     | Opens a separate Modbus/TCP connection with its own timeout and message spacing, which other integrations cannot change.     |
| Use direct connection and close it after each poll        | Same as above, and also closes the connection after every poll so that the inverter is free for other clients between polls. |

A direct connection avoids the shared timeout and spacing, but an inverter
accepts few TCP connections at once, so two clients holding it open can still
fight over it.

## 6. Other shared-connection limits

- **Link settings conflicts.** If another integration holds the same device over
  different link settings, one shared connection cannot honor both, and setup
  fails with the `link_settings_in_use` error.
- **Disconnect is shared.** `SharedUnits.disconnect()` drops the link so the next
  request reopens it, which closes it for every unit on that connection.
- **Nothing to close on unload.** The `modbus` integration owns the connection
  and closes it behind the last entry holding a unit.

## 7. Reducing the bad first experience (ideas, not implemented)

_Written by Claude Code as a discussion of options; nothing here is built yet._

The main concern is that users try the built-in SolarEdge Modbus integration,
which Home Assistant now offers to everyone by default, or find this
integration later. Merely trying the built-in one raises the shared timeout
(section 2), and the user then sees slow or missing data from this integration
and blames it, although the cause is outside it.

What exists today: the readme warning, and the "Another Integration Shares This
Inverter" repair issue, whose text already suggests _Use direct connection_.

Gaps:

- It is `is_fixable=False`, so the user must find the options page alone.
- Nothing detects the cause, a shared timeout far above ours, directly. The
  repair issue only knows another integration is present.
- The readme warning is aimed at people who already know about the conflict.

Options, least to most invasive:

1. **Say it is not a fault of this integration.** In the log warning and the
   repair text, state that the shared connection is running at a long timeout
   because another integration asked for it. Cheap, and it addresses the blame.
2. **Make the repair fixable** with a one-click switch to direct connection, so
   the user does not need to understand the cause. Direct connections have a
   cost of their own (an inverter accepts few TCP connections at once), so this
   needs a decision before it becomes the suggested fix.
3. **Detect the cause up front.** If the shared connection's timeout is already
   far above ours at setup, raise the repair immediately instead of waiting
   for slow refreshes. Not checked: whether `modbus_connection` exposes the
   effective timeout.
4. **Make direct the default for new installs.** Avoids the problem for people
   who add this integration after the built-in one, but reverses the decision
   to use the shared connection by default.
5. **Move the readme warning higher** with a plain-language heading such as
   "Installed the built-in SolarEdge integration first?", so people find it by
   symptom.

Recommended low-risk set: 1, 3 and 5. Option 2 follows if steering users to
direct mode is acceptable.
